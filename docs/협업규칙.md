# 협업 규칙

워크샵에서 정한 대로 모든 작업에 WBS 번호를 붙입니다. 번호 형식은 `대분류.중분류.작업`(예: `2.3.1`)이고 작업 하나는 하루에서 이틀 크기입니다. WBS 번호는 이슈 제목, 보드의 WBS 필드, 커밋 메시지에 쓰고, 브랜치 이름에는 이슈 번호를 씁니다. WBS는 일정이 바뀌면 번호가 다시 매겨질 수 있고 작업 하나에서 PR이 여러 개 나오기도 해서, 겹치지 않는 이슈 번호로 브랜치를 구분합니다.

## 작업 한 번의 흐름

1. 이슈를 만듭니다. 제목은 `[2.3.1] 환불 API 구현`이고 "WBS 작업" 템플릿을 씁니다. 이슈 하나에 담당자는 한 명입니다.
2. `develop`에서 이슈 번호로 브랜치를 땁니다. 이슈가 12번이면 아래처럼 만듭니다.
   ```bash
   git switch develop
   git pull
   git switch -c feat/12-refund-api
   ```
3. 커밋하고 push한 뒤 Discord `#커밋현황`에 커밋 메시지를 그대로 붙여 넣습니다.
4. `develop`으로 PR을 엽니다. 본문에 `Closes #이슈번호`를 꼭 넣어야 머지할 때 이슈가 닫히고 보드 상태가 Done으로 바뀝니다.
5. 리뷰어 한 명 이상이 승인하면 머지하고 `#머지현황`에 남깁니다.

## 브랜치

| 브랜치 | 용도 | 규칙 |
| --- | --- | --- |
| `main` | 배포 기준 (AWS 자동 배포 대상) | `develop`에서 PR로만 합칩니다 |
| `develop` | 개발 통합, 기본 브랜치 | 기능 브랜치에서 PR로만 합칩니다 |
| `feat/이슈번호-작업명` | 기능 개발 | 예: `feat/12-refund-api` |
| `fix/이슈번호-작업명` | 버그 수정 | 예: `fix/15-refund-amount` |
| `refactor/`, `docs/`, `chore/` + `이슈번호-작업명` | 구조 개선, 문서, 설정 | 예: `docs/18-api-spec` |

작업명은 영어 소문자와 숫자, 하이픈(`-`)만 씁니다. PR을 열면 CI가 브랜치 이름과 `Closes #`를 검사합니다.

`main`과 `develop`에는 직접 push할 수 없습니다. `develop`은 승인 1개와 CI 통과, `main`은 승인 1개가 있어야 머지됩니다.

기능 브랜치를 `develop`에 합칠 때는 Squash and merge를 써서 PR 하나가 커밋 하나로 남게 합니다. `develop`을 `main`에 합칠 때는 Create a merge commit을 씁니다.

## 커밋 메시지

첫 줄은 `[머리말]_WBS번호/요약`, 다음 줄부터 바뀐 내용을 `-`로 적습니다.

```
[Add]_2.3.1/RefundApi
- 환불 금액 검증 추가
- 부분 환불 예외 처리
```

머리말은 네 가지만 씁니다.

| 머리말 | 언제 |
| --- | --- |
| `[Add]` | 기능, 파일 추가 |
| `[Fix]` | 버그 수정 |
| `[Refactor]` | 동작은 그대로 두고 구조 개선 |
| `[Docs]` | 문서, 주석 |

## PR

- PR 하나에는 이슈 하나만 담습니다. 너무 커지면 나눠서 올려 주세요.
- 제목은 이슈 제목과 같게 `[2.3.1] 환불 API 구현`으로 씁니다.
- 화면이 바뀌면 스크린샷을, API가 바뀌면 요청·응답 예시를 붙입니다.
- AI가 만든 코드도 본인이 읽고 이해한 다음 올립니다. 리뷰어가 물어보면 설명할 수 있어야 합니다.

## 리뷰

- 리뷰 요청을 받으면 그날 안에 봐 주세요.
- 꼭 고쳐야 하는 문제(버그, 보안, 빌드 실패)는 Request changes로, 취향 차이는 코멘트로만 남깁니다.

## 비밀 정보

API 키, DB 비밀번호, AWS 자격 증명은 절대 커밋하지 않습니다. `.env`로 관리하고 예시는 `.env.example`에 값 없이 남깁니다. 실수로 올렸다면 바로 팀장과 클라우드 담당자에게 알리고 키를 폐기합니다.
